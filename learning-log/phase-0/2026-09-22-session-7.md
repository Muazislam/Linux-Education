## Objective
Establish a solid mental model of processes in Linux, distinguishing between binary executables stored on disk within `$PATH` and active, stateful process instances managed by the kernel in RAM via Process IDs (PIDs).

## What I Practiced & Explored
1. **Conceptual Demystification**:
   - Mapped GUI tools to CLI primitives:
     - Application Launcher $\rightarrow$ Searching the `$PATH` directory list via `which`.
     - System Monitor $\rightarrow$ Inspecting kernel process tables via `ps`, `pgrep`, and interactive dashboard `top`.
2. **The 4 Process States Tested & Verified**:
   - **State A (Not Installed)**: Executed `which nginx`. Verified that `which` traversed all directories in `$PATH` (e.g. `/usr/bin`, `/usr/local/bin`, pyenv, nvm) and reported negative existence.
   - **State B (Installed, Not Running)**: Executed `which geogebra` (confirmed `/usr/bin/geogebra` exists on storage disk) and tested `pgrep -l geogebra` (returned empty, proving no active PID or memory allocation).
   - **State C (Running Normally)**: Executed `which konsole` and `pgrep -l konsole`. Verified live PID `73426` assigned by the kernel.
   - **State D (High Resource Consumption)**: Executed `top`. Observed system load averages (2.14, 1.88, 1.40), memory breakdown (8056 MiB used / 2711 MiB free), and identified real-time CPU consumers (`firefox` PID 1851 at 32.7% CPU, `kwin_wayland` PID 1468 at 21.8% CPU).
3. **Exploratory Learning**:
   - Investigated `pgrep --help` options (`-l`, `-a`, `-c`, `-f`, `-u`).
   - Dissected why `ps` showed two PIDs in an interactive shell (one for the parent `bash` shell, one for the transient `ps` command itself).
